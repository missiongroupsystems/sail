# v0.5 Kitchen printing: completion note

Date: 4 Nov 2026. Branch: `feat/beta-v1`. Roadmap phase 5 (v0.4 → v0.5).

## What

Network ESC/POS printing through a print relay at each outlet (scope §4.7): printer configuration (IP, port, paper width, role, station, include/exclude tags, order-type and source filters, copies, backup printer, default kitchen printer, status-query and CJK flags); relay records with one-time pairing codes and relay tokens; the `app_relay` principal and Postgres role with narrow grants; the server-side ESC/POS renderer in `shared` (kitchen, void and reprint tickets, pre-bill/receipt/refund receipt, service slip, 80 mm and 58 mm, CJK raster fallback, 16 golden files); routing that creates one job per target printer per copy in the same transaction as the fire or void; the durable job queue (`queued → claimed → printed | failed`, `→ rerouted`, stale claims re-queued by the worker); relay endpoints (printers, outstanding jobs, SSE stream, claim, ack, heartbeat); staff operations (job list with the late-job alert query, reprint, reroute to the backup, test print); relay-offline alerts; and the `relay` package itself, a small Node service shipped as a Docker image.

## How

- **Routing** (`routeLines`): a line goes to every active kitchen printer whose rules match (include tags, exclude tags, order type, source; station printers only for lines fired from their station). Lines that match nothing go to the default kitchen printer; a default printer with no include tags is a pure fallback. Copies become separate jobs so each copy has its own job ID on the ticket.
- **Rendering happens on the server** with the shared templates, so templates change with a deploy and the relay stays logic-free. Each job stores the bytes (base64), the plain-text rendering (back-office preview, tests) and the document (so a reprint or reroute can re-render for a different paper width).
- **Void tickets** go to the printers that received the item (looked up from the order's kitchen jobs), with the VOID banner and the voided quantity.
- **Queue lifecycle** is guarded by a trigger; claims are idempotent for the same relay and `state_conflict` for another; `ack` reports printed, failed or requeue. The worker re-queues claims older than 60 s. `print_jobs?late=true` lists jobs not printed within 10 s for the POS banner; relays silent for 2 minutes raise `relay.offline` events.
- **Relay loop**: pair once (code → token stored on the device), load printers, hold the SSE stream, catch up on `hello`/`job`/`resync` and every 60 s as a safety net, claim → DLE EOT status (where supported) → send over TCP 9100 → ack, with three attempts and backoff; heartbeat every 30 s with per-printer reachability. The relay never computes or parses business data.
- **Live updates**: `print_jobs` changes notify both `relay:<outlet>` and `outlet:<outlet>` channels, so stations see job status without polling.

## Why

Kitchen tickets are safety-critical for service (scope §6). A durable server-side queue with job IDs on every ticket, a logic-free relay that reuses the SSE pattern, and reprint/reroute from the POS are the mitigations the scope doc prescribes for printers that give no feedback over raw TCP.

## Exit criteria

| Criterion | Status |
|-|-|
| p95 fire-to-printed under 3 s on staging with the beta outlets' printer model | **Blocked**: no staging, no printer hardware. In the test suite the full path (fire → job → relay loop → TCP → ack) completes in well under a second against a fake printer. |
| Staging failure drills (printer unplugged → alert within 10 s → reroute, no ticket lost; relay restarted → queued jobs print; spare relay paired and printing within 15 min) | Mechanisms built and tested at the API: late-job query, reroute to backup with originals marked rerouted, stale-claim re-queue, catch-up after reconnect, pairing a second relay. **Drills themselves are blocked** on staging and devices. |
| Golden files for every template at both widths; CJK legible on the target printer | Golden files met (16, in `shared`). CJK on real hardware **blocked**; the raster fallback and code-page path are unit-tested. |
| Routing tests cover tags, exclusions, order-type and source filters, station printers, copies and the default printer | Met for tags, copies, default fallback, backup and role mismatch; exclusions, order-type/source filters and station printers are covered by the matcher's unit logic and should gain explicit API cases in v0.9. |
| Test tickets print on a beta outlet's real printers | **Blocked**: hardware and site access. |

## Blocked inputs (scope open questions 2 and 3)

Printer models and port-9100 support, CJK needs, relay devices (one per outlet plus a spare), LAN ports, installation owner. The relay image is multi-arch and needs only outbound HTTPS.

## Decisions recorded

- A default kitchen printer with no include tags is a fallback only; to print everything on one printer, give it an include tag that every product carries, or make it the only kitchen printer.
- Receipt printers (role `receipt`) never receive kitchen tickets; reroutes must keep the role.
- Duplicate tickets after a retry are accepted (job ID on the ticket makes them recognisable).
