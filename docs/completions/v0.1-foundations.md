# v0.1 Foundations: completion note

Date: 4 Nov 2026. Branch: `feat/beta-v1`. Roadmap phase 1 (v0.0 → v0.1).

## What

A walking skeleton on Launchpad's patterns with Sail's §10.1 changes: a pnpm/Turbo monorepo; a Hono + `@hono/zod-openapi` API with a committed OpenAPI spec; postgres.js on the pooler with `prepare: false` plus a session connection for LISTEN and migrations; one transaction per request behind an admission gate with `set_config('app.current_*')` and `SET LOCAL ROLE`; Idempotency-Key storage and replay; an append-only event log with per-outlet sequences, `pg_notify` triggers, SSE fan-out with heartbeats and `resync`; the organisation model (merchant, settings, brands, outlets, stations), staff with the five fixed roles and outlet/brand scope, the permission matrix in `shared`, a single audit writer, and the operation manifest. The back-office shell (`packages/web`, `packages/ui`) is built against the same contract.

## How

- **Tests run on real Postgres without Docker.** The user running this build has no Docker socket access, so the harness drives the Postgres 17 binaries shipped by `@embedded-postgres/linux-x64` directly (`test/pg.ts`): `initdb`, `pg_ctl`, a template database built from the migration journal, and one cloned database per test file. The same harness powers `pnpm dev:local`.
- **RLS replay is generic.** `test/rls-replay.test.ts` discovers every table with a `merchant_id` column, asserts RLS is on with a policy, and proves merchant A cannot see merchant B's rows and that an outlet-limited cashier sees only their outlet. New tables are covered automatically.
- **Manifest-driven permissions.** `defineOp` reads `OPERATIONS[op]` for `min_role`, allowed principal kinds and the `x-sail` extension; a contract test fails on any `/v1` route without one.
- **Drizzle + raw postgres.js in one transaction.** Drizzle's postgres-js driver needs a top-level client with `options`; the request transaction handle is given the pool's options. Drizzle installs transparent timestamp and JSON serializers, so raw queries pass ISO strings and `JSON.stringify(...)::jsonb` (recorded in `docs/how-to.md`).
- **LISTEN resilience.** `pg_terminate_backend` on the LISTEN connection is covered by a test: postgres.js reconnects, `onlisten` fires again, every open stream receives `resync`, and the next event arrives through the new connection.

## Why

The scope doc makes the API the only writer of money and state (§7.1), and every later phase adds tables, principals and streams to this pipeline rather than inventing new patterns (roadmap §1, principle 2). Building the harness on real Postgres (not a mock) is what makes the RLS and invariant tests meaningful.

## Exit criteria

| Criterion | Status |
|-|-|
| A trivial change goes from PR to staging automatically, and to prod only after approval, with migrations on staging first and drift checks | **Blocked: no Supabase, Fly or GitHub secrets in this environment.** The pipeline is written (`ci.yml`: test → `deploy-staging` on `main` → `deploy-prod` behind the `production` environment, gated by `vars.DEPLOY_ENABLED`), with `db:migrate` doing drift check → migrate → drift check. Needs: `STAGING_DATABASE_URL`, `PROD_DATABASE_URL`, `FLY_API_TOKEN`, Fly apps `sail-api` and `sail-api-staging`, a Supabase branch for staging, Vercel projects. |
| The OpenAPI CI check fails on an unreviewed spec change | Met: `openapi:check` compares the generated document with the committed `openapi.json`. |
| RLS replay: two seeded merchants cannot see each other's rows; outlet scoping works for a staff member limited to one outlet | Met: `test/rls-replay.test.ts` and `test/foundations.test.ts`. |
| The test SSE stream reconnects and catches up after a rolling deploy, after the LISTEN connection is killed, and after an iPad Safari tab is backgrounded | Partly met: LISTEN kill → `resync` → catch-up is tested. Rolling deploy and iPad backgrounding need staging and a device; the client catch-up hooks (reconnect, gap, visibility, resync) are part of the web client work and are exercised on staging in v0.9. |
| A back-office user can log in, create a brand and outlet, add staff with a role and outlet scope; each action appears in the audit log | Met at the API (tested) and in the back-office shell (web verification in the v0.1 web report below). Supabase email login is wired but untested without a project; the development sign-in path is tested. |
| The 503 alert fires in a staging test that saturates the admission gate | Partly: the gate returns 503 `overloaded` and `/health` exposes `gate.rejected` (unit-tested). Alerting tooling is **blocked** on the observability decision (roadmap §6); structured pino logs are in place. |

## Decisions and deviations recorded

- Embedded Postgres instead of Docker for tests and local development (environment constraint; CI can use either).
- Four token kinds signed by Sail (`station`, `pin`, `guest`, `relay`, `agent`) as HS256 JWTs with a `typ` claim and separate secrets; back-office tokens from Supabase (JWKS or HS256) or `DEV_AUTH_SECRET` outside production.
- Merchant onboarding is a script (`bootstrap`), as self-serve onboarding is deferred (scope §5).
- Observability tooling: not chosen (needs a decision with Launchpad's engineer). Pino structured logs with request IDs are in place; `/health` exposes gate and SSE counters for a scraper.
- Supabase backups and point-in-time recovery: not confirmable without the project; listed as a v0.9 blocker.
