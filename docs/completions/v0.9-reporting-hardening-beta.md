## How

- **Reports** never re-price anything: every figure is a sum of cents the register wrote (order totals, line amounts, adjustments, payments, refunds). The sales summary test checks its totals against direct sums over the tables. Filters: outlet, date range, brand, station, shift, source, order type, staff, category. CSV is one flat file per report; the daily PDF is the Z-report plus breakdowns.
- **Agents** (vision §7): an identity has a role, scope, toolsets, a ceiling (T0 to T2) and budgets. A session lasts 15 minutes and may act on behalf of a person, taking the lower role and the intersection of outlets. The `app_agent` Postgres role is granted generically over every tenant table except token, pairing and session tables, with column-level grants that exclude PIN hashes, token hashes, auth subjects and customer contact columns, and writes only on operational tables. `defineOp` compares the operation's tier with the caller's ceiling after the role check: reads and dry runs always run; anything else above the ceiling is stored as a **proposal** (frozen method, path, body, idempotency key, expected version) and answered with 202 `requires_confirmation`. A staff member with the operation's role approves; the register replays the frozen request as the approver through the ordinary pipeline, so the same checks apply and a changed target fails with `version_conflict`. Approvals of T3 operations need Manager+. Staff can carry ceilings too (the `risk_ceiling` column), for trainees.
- **MCP** is generated from `openapi.json` and the `x-sail` manifest: tool name, description (summary, description, tier, role, emitted events, proposal behaviour), JSON schema (path and query parameters, `body`, `idempotency_key`, `rationale`, `dry_run`). `tools/list` is filtered by the identity's toolsets and role; above-ceiling tools are marked proposal-only. Every call is `app.request` with the agent's bearer; responses wrap outside text as `untrusted_text`. The adapter is stateless Streamable HTTP, one server per request, and runs from the same image as `--role=mcp`.
- **Nested requests** (a proposal approval replays a request inside the approver's request) exposed a deadlock on the approver's session row; session last-seen updates now use `FOR UPDATE SKIP LOCKED`.
- **Load test** (`pnpm --filter @sail/server load:local`, 20 stations × 10 orders each with 50 SSE streams open, TX_MAX 16, embedded Postgres on the development machine):

| Operation | Calls | p50 ms | p95 ms | p99 ms |
|-|-|-|-|-|
| orders.get | 400 | 34 | 63 | 78 |
| floor.snapshot | 200 | 31 | 60 | 73 |
| orders.open | 200 | 133 | 797 | 1073 |
| lines.add | 200 | 137 | 593 | 938 |
| orders.fire | 200 | 147 | 833 | 1198 |
| payments.record | 200 | 184 | 619 | 1774 |

  126 requests/s, no admission-gate rejections, 143 050 SSE events delivered. Reads meet the 300 ms target with room to spare. Mutations meet it at p50 but not at p95 under 20 writers saturating one small Postgres; the write path spends its time in pricing, events and print-job creation inside one transaction. This is the figure to beat on staging with a real Postgres and Fly sizing; the knobs are machine count, `TX_MAX` and `DB_POOL_MAX`.

## Why

Reports as views keep one source of truth and let RLS apply to reporting. The agent principal, ceilings and proposals exist so an assistant can be connected later without a second permission model: it reaches the same button through the same check, and a human holds the second key for the dangerous ones. Generating the MCP surface from the spec means a tool cannot drift from the API and exposure is a reviewed, committed change.

## Decisions recorded

- Reports use plain security_invoker views rather than materialised views refreshed by the worker; revisit when a report takes over a second on production data.
- Above-ceiling tools remain in `tools/list` marked proposal-only, because proposals are the intended path for them (vision §7.4) and hiding them would push agents to improvise.
- Proposal approval replays the frozen request as the approver; the proposal's events and audit entry link the agent identity and the approver through the correlation id.
- Agents cannot read customer contact columns at all in v0.9 (no masked view yet).
- Operation budgets are per 15-minute session (`max_ops_per_hour` applied per session); a shared counter across sessions is a v1.0 item.
- The local load test is an in-process harness, not a network test; it measures the register, not Fly or the network path from Singapore.
