# v0.8 Scan to Order: completion note

Date: 4 Nov 2026. Branch: `feat/beta-v1`. Roadmap phase 8 (v0.7 → v0.8).

## What

Guests at a dine-in table scan a QR code and send rounds to their table's open order from their phones; staff accept and fire them at the POS; the bill is paid at the POS as usual. Guests never pay (scope §4.6). Register side: permanent, rotatable table tokens and a printable QR sheet (PDF); guest sessions with short-lived guest tokens scoped to one table and its open order; rate limits per device and per table; the `app_guest` principal and narrow Postgres role (menu and own order only, no payments); guest rounds (held for acceptance or fired straight away, per channel link), accept/reject at the POS; table requests (up to 5 configured plus call for bill, with an optional printed slip, and call for bill marking the table); the guest's view of the table's order (menu prices only, round statuses); a per-order guest stream; session expiry when the order closes; "open on first scan" per channel link; QR rounds tagged by source for printer routing and reports. The guest web app is delegated UI work against this contract.

## How

- **Tokens:** the QR URL carries an opaque token; only its SHA-256 is stored. Rotating (per table or by generating a sheet) retires the old token. `POST /v1/guest/sessions` is public, rate-limited per device hash and per table, and returns a 4-hour guest JWT bound to the session row; the resolver refuses revoked or expired sessions.
- **RLS for guests** sets `app.current_order` to the session's order; `app_guest` may read the catalogue, outlet, its own order and lines, its own rounds, requests and session, and nothing else (no checks, payments, staff). Guest writes are executed by the register as a system actor (`asSystem`: `SET LOCAL ROLE app_authenticated` for the validated operation, then back), so the write surface granted to `app_guest` stays read-only.
- **Rounds** reuse `buildLines` (same menu, availability, caps and modifier rules as the POS), insert lines with `source: guest` and the round id, and either hold (`status held`, round pending) or fire immediately (kitchen tickets through the same `createKitchenJobs`). Accept fires and prints; reject voids with the reason and releases caps.
- **Invariant triggers are `SECURITY DEFINER`** so deferred checks at commit do not depend on the committing role's grants; the order-total trigger re-reads the row (an order opened and priced in one transaction exposed the old `NEW.total` comparison).
- **Live updates:** QR rounds appear on the POS through the existing outlet stream (`round.submitted`) and on the floor as a pending-rounds badge; guests follow `order:<id>` on `/v1/guest/stream`.
- **Closing:** completion or cancellation revokes the order's guest sessions immediately (hook) and a worker revokes stale/expired sessions as a safety net.

## Why

Scan to Order is a shortcut for keying in orders, not a payment channel (scope §4.6). Keeping guest principals read-only in the database and running every mutation through the same register primitives means prank or abusive traffic can never do more than add lines that staff can see, hold and reject.

## Exit criteria

| Criterion | Status |
|-|-|
| p95 time for a guest round to reach the POS under 2 s | Met in the test suite (the round is on the POS stream within the same second); real-network p95 needs staging. |
| A photographed QR code for a table with no open order cannot create an order (default) | Met (`table_not_open` state conflict; menu stays browsable). |
| Guest tokens cannot read other tables, other orders or any payment data | Met at the API (staff endpoints 403; snapshot shows no totals/payments; RLS policies scope to the session's order). An `app_guest` RLS replay case for the payment tables is a v0.9 addition to the generic replay test. |
| Rate limits hold under a scripted burst from one device and one table | Met (12 sign-ins from one device → 2 limited; repeated requests of one kind limited). |
| A guest and a station adding to the same order at once both succeed with no lost lines | Met. |
| Tested on iOS Safari and Android Chrome; a printed sheet scans | **Blocked**: devices and a printed sheet; the PDF renders and the URL format is fixed. |

## Decisions recorded

- Rate limits are in-process (per API machine); the admission gate still protects the database. A shared store is a v1.x refinement if abuse appears.
- When an outlet has Scan to Order links for several brands, the first enabled link is used for the table; a per-table brand mapping is deferred.
- The guest stream needs an order; before one exists the guest app polls `guest.order`.
- Guest round rate limiting counts only successful submissions, so a guest fixing a missing choice is not blocked.
