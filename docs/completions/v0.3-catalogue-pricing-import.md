# v0.3 Catalogue, pricing configuration and legacy import: completion note

Date: 4 Nov 2026. Branch: `feat/beta-v1`. Roadmap phase 3 (v0.2 → v0.3).

## What

The register side of the catalogue: products and components with per-order-type prices, tags and the BCRS flag; modifier groups with min/max, per-modifier maximum and price overrides, nested to two levels (enforced in the database); the two-level report-category tree; brand menus with sections, one level of sub-sections and item placements; availability rules (outlet, channel, weekday, time window); per-outlet 86 and daily caps with an atomic decrement; channels links (POS, Scan to Order) with their Scan to Order settings; areas and tables; tender types and void reasons; POS layouts (pages > folders > tiles, 12 curated colours); customers and customer groups; versioned pricing rules with scheduled activation, a simulator that runs the v0.2 engine on persisted rules, and validation warnings; the CSV legacy importer with dry-run reports, apply, and idempotent re-runs; a compiled menu per channel link for the POS and the guest app. The back-office screens for these (menu builder, pricing section with simulator, customers, import review) are built against this contract; see the web status below.

## How

- **Rule versions are rows.** `rule_key` is the identity the engine sees as `rule.id`; the active set at time T is "newest non-archived version with `effective_from ≤ T`" (one `DISTINCT ON` query), so correctness never depends on the worker. The worker only flips `status` and emits `pricing_rule.activated` for the UI. A trigger makes versions immutable.
- **The simulator is the engine.** `POST /v1/pricing/simulate` expands product references from the catalogue, loads the active rules and calls `price()`. The test replays every seed-rule reference case through it.
- **Stock is enforced in SQL.** Daily caps decrement with a single conditional `UPDATE ... RETURNING` and a `CHECK (cap_remaining >= 0)`; a test fires three concurrent decrements at a cap of 2 and exactly two succeed.
- **The importer runs in one transaction on the worker.** A dry run throws a rollback sentinel after building the report; apply commits. Rows match by `legacy_id` (products by SKU, customers by mobile) so a re-run of an unchanged export yields zero creates and updates (tested), and an edited export updates in place (tested). Layouts are assembled from one row per tile into pages and folders, with legacy colours mapped to the 12 tile colours.
- **The compiled menu** resolves modifier prices (override, else the modifier product's price), parent categories, availability "now" and sold-out/cap state, and carries a `version` for client caching.

## Why

Real menus at real scale have to be in Sail before the POS exists (roadmap §1, principle 3), and pricing rules must be persisted, versioned and simulated against the real catalogue before live orders use them (§4.8).

## Web (back office) status

The v0.3 screens (menu builder with drag-and-drop ordering and bulk price edit, pricing rules with simulator and warnings, customers and groups, CSV import review as a change-style report) are delegated UI work against this contract; their state is recorded in the web completion notes as they land.

## Decisions recorded

- Products belong to the merchant with an optional `brand_id` (null = shared), so a group with shared components does not duplicate 20,000 rows per brand.
- Availability rules are allow-lists: no rules means always available; any matching rule makes the target available.
- Open orders are priced with the rule set active at the time of re-pricing; the adjustments store the rule snapshot. Frozen results (v0.6) keep paid checks stable.
- Order numbers are per outlet and never reset (`P-0001`, `QR-0001`), avoiding ambiguity across the business-day cutoff.
